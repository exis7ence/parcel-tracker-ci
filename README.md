# Parcel Tracker — учёт посылок

Учебное консольное приложение на Go для работы с посылками и их статусами. Данные хранятся в SQLite, код разделён на сервисный слой и слой доступа к данным. Репозиторий также содержит Dockerfile и workflow для проверки кода и публикации контейнерного образа.

Проект выполнен в рамках обучения в Яндекс Практикуме. В go.mod сохранено имя модуля исходного учебного проекта.

## Возможности

- Регистрация посылки с адресом и идентификатором клиента.
- Получение посылки по номеру и списка посылок клиента.
- Последовательные статусы: `registered` → `sent` → `delivered`.
- Изменение адреса и удаление посылки только в статусе `registered`.
- Хранение данных в SQLite и проверка операций с базой тестами.

Запуск выполняет демонстрационный сценарий из main.go: регистрирует посылки, меняет адрес и статус, выводит результаты. Приложение не запускает HTTP-сервер и не предоставляет интерактивное меню.

## Стек

Go, database/sql, SQLite (modernc.org/sqlite), testing, Testify, Docker, GitHub Actions.

## Структура

```text
main.go                 Модель Parcel, сервис ParcelService и пример использования
parcel.go               ParcelStore и SQL-запросы
parcel_test.go          Тесты операций с SQLite
tracker.db              База данных со схемой, используемая приложением и тестами
go.mod, go.sum          Модуль и зависимости
Dockerfile              Сборка консольного приложения
.github/workflows/      Проверки и публикация Docker-образа
```

## Локальный запуск

Нужны Git и Go версии не ниже 1.22.0, указанной в go.mod. Команды приведены для Bash, в том числе Ubuntu/WSL.

```bash
git clone https://github.com/exis7ence/parcel-tracker-ci.git
cd parcel-tracker-ci
go mod download
go run .
```

Результат демонстрационного сценария выводится в терминал. Запускайте команды из корня проекта: программа открывает tracker.db относительно текущего каталога.

### Особенность базы данных

Текущая версия использует включённый в репозиторий файл tracker.db. Приложение не создаёт таблицу parcel автоматически. Если убрать этот файл, SQLite может создать пустую базу, но запросы завершатся ошибкой отсутствия таблицы.

Пример и тесты изменяют базу, поэтому для знакомства с проектом используйте отдельный клон с учебными данными. Локальные изменения tracker.db не требуется отправлять в репозиторий.

## Тесты и статический анализ

Отдельно запускать приложение перед тестами не требуется: тесты непосредственно обращаются к SQLite.

```bash
go test -count=1 -v ./...
go vet ./...
```

Тесты проверяют добавление и получение посылки, удаление зарегистрированной посылки, обновление адреса и статуса, выборку по клиенту. Они используют файл tracker.db и могут оставлять в нём тестовые записи.

## Docker

```bash
docker build -t parcel-tracker .
docker run --rm parcel-tracker
```

Образ собирает приложение для Linux/amd64. Контейнер выполняет консольный сценарий и завершается; проброс портов не требуется.

База копируется в образ при сборке. При запуске без подключённого тома изменения базы остаются внутри контейнера и удаляются вместе с ним при использовании --rm.

## GitHub Actions

Workflow `.github/workflows/push.yaml` содержит два этапа:

1. **Проверки:** `go test -v ./...` и `go vet ./...` в контейнере Go 1.22. Запускаются при push в main или feature/ci-cd, push тегов v* и pull request в main.
2. **Публикация образа:** запускается после успешных проверок для тега v*. Собирает и отправляет образ в Docker Hub.

Для публикации в настройках репозитория должны быть заданы GitHub Actions secrets:

- `DOCKER_USERNAME` — имя пользователя Docker Hub.
- `DOCKER_ACCESS_TOKEN` — токен доступа для публикации образа.

Наличие workflow не означает, что эти секреты уже настроены. Без них публикация образа не выполнится. Результаты конкретных запусков доступны на вкладке Actions.

## Что показывает проект

- Разделение бизнес-операций и SQL-запросов.
- Использование параметров SQL-запросов через sql.Named.
- Обработку результатов QueryRow и Query, закрытие rows и проверку rows.Err.
- Проверку операций с реальной SQLite-базой.
- Автоматизацию тестов и статического анализа, сборку Docker-образа.

## Ограничения и дальнейшие улучшения

- Добавить создание схемы или миграции вместо зависимости от готового файла базы.
- Перевести тесты на отдельную временную базу, чтобы они не меняли данные приложения.
- Добавить тесты запрещённых операций: изменение адреса или удаление после отправки.
- Различать успешное изменение и ситуацию, когда SQL-запрос не затронул ни одной строки. Сейчас SetAddress и Delete при невыполненном условии могут вернуть nil.
